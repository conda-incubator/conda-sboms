# AGENTS.md — conda-sboms coding guidelines

## Project structure

- `conda-sboms` is a conda plugin that generates software bills of materials
  through conda's environment exporter hook.

- `conda_sboms/plugin.py` contains only hook registration. Keep its imports of
  format implementations lazy because conda loads plugin modules on every
  invocation.

- Each SBOM format lives in its own module at the package root.
  `conda_sboms/cyclonedx.py` owns CycloneDX rendering and mapping, and
  `conda_sboms/spdx3.py` owns SPDX 3 rendering and mapping.

- Do not introduce a format-neutral SBOM model before two real exporters need
  one. Share a normalized conda package graph only when concrete duplication
  between formats justifies it.

- Tests mirror format modules. Tests for `conda_sboms/cyclonedx.py` live in
  `tests/test_cyclonedx.py`, and SPDX tests live in `tests/test_spdx3.py`.
  Test multi-format hook registration in `tests/test_plugin.py`.

- `conda_sboms/_version.py` is generated by hatch-vcs. Do not edit it manually.

## Imports

- Use relative imports for intra-package references. Absolute `conda_sboms.*`
  imports belong in tests and entry points.

- Inline imports are reserved for `plugin.py` hook implementations and optional
  dependencies. Put other imports at the top of the module.

## Dependencies

- Minimize the dependency graph. Prefer the standard library, conda APIs, and
  already-required packages over new dependencies.

- Use the official library for each supported SBOM format when it provides the
  required schema version and model. The CycloneDX exporter uses
  `cyclonedx-python-lib` and `packageurl-python`.
  SPDX 3.0.1 is an explicit exception. Build its focused document structures
  with dictionaries and the standard-library JSON serializer, and validate
  against official JSON Schema and SHACL resources in tests. Do not add an
  SPDX SDK, generated model, or RDF runtime dependency.

- Pin supported version ranges in `pyproject.toml`, not exact runtime versions.

- Conda is required at runtime but is not distributed on PyPI. Keep that
  dependency documented in `pyproject.toml` and declare it in the conda package
  recipe when packaging is added.

## Typing and linting

- Use modern annotations such as `str | None` and `list[str]`.

- Use `from __future__ import annotations` in every hand-written Python module.

- Use `ruff` for linting and formatting. Its configuration lives in
  `pyproject.toml`.

## Code structure

- Before adding a class or method, check whether conda,
  `cyclonedx-python-lib`, `packageurl-python`, or the standard library already
  provides the operation.

- Prefer cohesive classes when format mapping, dependency graph construction,
  and serialization share input or derived state. Reserve module-level
  functions for framework callbacks, required APIs, or operations with no
  meaningful object owner.

- Keep `CycloneDXExportMetadata`, `CycloneDXPackage`,
  `CycloneDXDependencyGraph`, and `CycloneDXExporter` as the public object API.
  Keep their mapping, graph, and serialization behavior on those classes rather
  than moving it into private classes or standalone private helpers.

- Do not create stateless utility classes or methods that only wrap one
  expression. Inline short one-use glue in the class that owns it.

- Do not create a public utility or shared module until a second format needs
  the same behavior. Keep format-specific functions in their format module.

- Do not use section comments to group functions or tests. Rely on ordering and
  module boundaries. If a file needs section headings, split it by behavior.

- Comments explain non-obvious intent, trade-offs, or upstream constraints.
  Do not narrate what the next line already says.

## Exporter design

- Register exporters with `conda_environment_exporters`. A single-platform
  exporter receives one `conda.models.environment.Environment` and returns a
  string. It does not receive CLI arguments, an output path, a workspace, or a
  raw lockfile.

- Keep exporters generic to conda. They must work with `conda export` and with
  clients such as conda-workspaces without importing or discovering those
  clients.

- Require `Environment.explicit_packages` when a format promises a resolved
  package inventory. Do not solve, read an installed prefix, or access the
  network from an exporter callback.

- Use `Environment.requested_packages` for product root edges when present.
  When it is absent, document and test any graph-root inference. Do not call
  inferred roots authoritative top-level requirements.

- Map dependency edges from `PackageRecord.depends` through `MatchSpec`. Do not
  treat `constrains` entries as installed dependencies.

- Preserve exact package identity with available hashes, source URL, build,
  subdir, filename, and other useful record fields. Keep conda PURL construction
  isolated because no accepted conda Enhancement Proposal currently defines an
  SBOM or conda PURL contract.

- Never infer a package supplier, producer, author, or manufacturer from its
  channel. Preserve arbitrary legacy license text as a named license unless it
  has been validated as an SPDX expression. In SPDX, retain an unrecognized
  label as conda metadata and make no declared-license assertion. Do not invent
  the full license text required for a custom SPDX license.

- Do not expose local prefix paths, credentials, channel tokens, signed query
  parameters, or fragments. Use conda's URL sanitizers and strip query strings
  before emitting distribution references.

- Make output deterministic for unchanged input when `SOURCE_DATE_EPOCH` is
  set. Sort components and graph edges, omit random identifiers, and fail on an
  invalid epoch rather than silently using the current time.
  Preserve CycloneDX's explicit reproducible mode, which omits the optional
  timestamp and ignores the epoch. SPDX reproducible mode requires a valid
  epoch because SPDX creation information requires a timestamp.

- State coverage gaps in the document. Use `unknown` when completeness cannot
  be established, and use `incomplete` only for a set with known omitted
  members. Conda package records cannot prove coverage of vendored content,
  statically linked libraries, operating-system components, virtual packages,
  or external package ecosystems.

- Keep compliance claims narrow. An SBOM can contribute to CRA technical
  documentation, but generating one does not establish product conformity.

## CycloneDX

- Emit CycloneDX 1.7 JSON by default. Also support CycloneDX 1.7 XML and
  explicitly selected 1.6 JSON. Keep `cyclonedx-json` mapped to 1.7.
  Validate final documents against the official version-specific schemas.

- Identify the environment as the root application and each resolved conda
  package as a library component. Emit a dependency object for the root and
  every component, including known leaves.

- Mark root assembly completeness `unknown` when conda metadata cannot prove
  it, and `incomplete` when input data identifies omitted constituents. Mark a
  component's dependency set `incomplete` when a declared dependency target is
  absent from the resolved records.

- `cyclonedx-python-lib` 11.x cannot model `compositions` and always creates a
  serial number. Keep the post-serialization adjustment limited to removing
  `serialNumber`, adding `compositions`, and making empty dependency lists
  explicit. Explicit reproducible mode may also remove the optional timestamp.
  Use namespace-aware operations for XML and retain schema element order.
  Do not replace the rest of the official serializer with hand-built JSON or
  XML.

## Testing

- Tests are module-level `pytest` functions. Do not use `unittest.TestCase` or
  class-based grouping.

- Prefer real `Environment`, `PackageRecord`, and `MatchSpec` instances. Use
  pytest fixtures such as `monkeypatch` and `tmp_path` rather than mock objects.

- Parameterize repeated input cases. Keep fixtures local until more than one
  test module needs them.

- Test schema validity, exact field mapping, requested and inferred root edges,
  disconnected cycles, missing dependency targets, deterministic ordering,
  timestamps, hash validation, URL sanitization, coverage markers, and the
  no-explicit-records error.

- Invoke every output through a real `conda export` integration test, retaining
  coverage for `--format cyclonedx-json`. Check canonical names, aliases, and
  filename detection.

- Validate SPDX JSON structure and SHACL semantics, including a deliberately
  invalid document that must fail. Keep validators in test environments and
  use pinned local resources so validation does not download schemas or
  JSON-LD contexts.

- After changing code or tests, run `pixi run -e dev check`. Fix all lint,
  formatting, and test failures before considering the work complete.

## Lockfile maintenance

- After any change to `pyproject.toml` that affects pixi dependencies, features,
  tasks, platforms, or environments, run `pixi lock` and commit the updated
  `pixi.lock` with the change.

## Documentation

- Build the documentation with Sphinx and MyST Markdown. Organize it by
  Diátaxis: tutorials teach, how-to guides solve a specific task, reference
  pages state the exact contract, and explanation pages describe design and
  boundaries.

- Keep installation instructions consistent with the current release state.
  Do not publish a `conda install` or `pip install` command before that package
  exists.

- Document each format by its exact specification version and exporter name.
  Distinguish schema validity, conda environment coverage, draft standards, and
  legal conformity.

- Give a schema-versioned format a version-pinned canonical exporter name.
  Keep an unversioned alias for the current version and state that it can
  advance to a later supported schema. Older compatibility versions require
  explicit selection and must not take over existing aliases or filenames.

- Explain that `--from-history` preserves requested roots for installed conda
  environments. Explain current conda-workspaces lock export limitations
  without adding workspace-specific behavior to this plugin.

- Avoid describing draft conda CEPs or public-enquiry standards as accepted,
  harmonized, or binding.

## Pull request and issue descriptions

- Write GitHub issue and pull request bodies as one line per paragraph or bullet
  and let GitHub wrap them in the browser. Reserve hard wrapping for code fences,
  tables, and CLI help text.

- Keep commit subjects concise. Commit bodies may use normal terminal-oriented
  wrapping.
